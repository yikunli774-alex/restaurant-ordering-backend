## 二、顾客侧 ①:桌台 + 会话 + 参与者(数据模型)

### 概念(从零)
- **桌台 `dining_table`**:一张桌子,固定编号(T01),贴二维码。
- **会话 `table_session`**:一拨客人从坐下到结账 = 一个会话。**同桌同时只能有一个「进行中」会话**,否则两拨客人账目会混。顾客侧最关键的规则。
- **参与者 `participant`**:扫码进来的匿名顾客,发 token(只存哈希),同桌多人共享一个会话。

### 关键技巧:用「生成列 + 唯一索引」把铁律焊死在数据库里
会话表加一个**自动计算**的列 `active_table_id`:
```sql
active_table_id ... GENERATED ALWAYS AS (
  CASE WHEN status IN ('OPEN','PENDING_PAYMENT') THEN dining_table_id ELSE NULL END
) STORED,
CONSTRAINT uk_table_session_active UNIQUE (active_table_id)
```
- 会话进行中 → 这列 = 桌号;结束 → = NULL。
- MySQL 唯一索引**允许多个 NULL、但不允许两个相同的非 NULL**。
- 于是:同一桌的「进行中会话」最多一个;历史已结束会话(NULL)随便多少张。
- **好处**:这条规则由**数据库本身**保证——并发下(多个请求同时想在一张桌子开会话)也只有一个能成功,应用层不用加锁。这是后面并发正确性故事的地基。

### 写了什么
- `V3__create_tables_sessions_participants.sql`:三张表 + 埋一个 Demo Store 和两张桌子 T01 / T02。
- `table/TableSessionInvariantIntegrationTest`:证明铁律——插一个 OPEN 会话 OK;同桌再插第二个 OPEN → 被唯一索引拒(DuplicateKeyException);把第一个关掉后又能开新的。

### 验证 ✅
`./mvnw test` → **11 个全绿**。

## 三、顾客侧 ②:签名二维码 + 扫码加入会话

### 概念
- **签名桌码**:QR 内容 = `T01.<HMAC 签名>`。改桌号签名对不上 → 拒。防伪。
- **加入会话**:验签 → 找桌 → **找或建**活跃会话 → 发参与者 token(只存 SHA-256 哈希)。
- **并发**:同桌多人同时扫码,靠唯一索引「找或建」——一个建成功,其余撞唯一约束 → 捕获 → 改为加入那个会话。

### 关键并发坑:隔离级别
`join` 是一个事务。MySQL 默认 **REPEATABLE READ** 用「快照」:抢锁失败方在同一事务里重查会话会**看不到**赢家刚提交的行 → 误报找不到 → 500。
改成 `@Transactional(isolation = READ_COMMITTED)`:每条语句看最新已提交数据,失败方重查即见赢家会话并加入。这是并发编程经典坑,也是面试/简历可讲的点。

### 写了什么
- `table/TableCodeSigner`:HMAC 签 / 验桌码。
- `table/TableSessionRepository`:找桌、找或建活跃会话(捕获重复)、插参与者、读会话。
- `table/TableSessionService`:`join`(验签 → 找桌 → 找或建会话 → 发 token)、`getSession`;READ_COMMITTED 事务。
- `table/TableSessionController`:`POST /table-sessions/join`(公开)、`GET /table-sessions/{id}`(公开)。
- `table/StaffTableController`:`GET /staff/tables`(**需店员登录**,列桌 + 可打印的 QR 内容)——第一个被鉴权保护的业务接口。
- SecurityConfig 放行 join / get-session;新增错误码 `TABLE_CODE_INVALID`。

### 验证 ✅(18 个测试全绿)
`TableJoinIntegrationTest` 7 条:建会话 + 发 token / 二次加入复用同一会话 / 篡改签名 400 / 签名有效但桌不存在 404 / 读会话状态 / `staff/tables` 无 token 401、有 token 返回 QR / **16 线程并发扫码 → 恰好 1 个会话、16 个参与者**。

## 五、顾客侧 ③:参与者鉴权(第二道门)

### 概念
- 店员用 JWT(`Authorization: Bearer`);顾客用参与者 token(`X-Participant-Token`)。
- 过滤器读顾客 token → SHA-256 哈希 → 查参与者/会话 → 盖 `ROLE_PARTICIPANT`。
- 两道门互不通:`/table-sessions/**` 要 `ROLE_PARTICIPANT`,`/staff/**` 要店员角色。
- 「只能看自己这桌」:参与者属于会话 A,访问会话 B → 403。

### 写了什么
- `ParticipantPrincipal` / `ParticipantAuthenticationToken` / `ParticipantAuthenticationFilter`。
- `TableSessionRepository.findParticipant(hash)`。
- SecurityConfig:装参与者过滤器 + 顾客/店员路径各要各自角色。
- `GET /table-sessions/{id}` 加「只能看自己这桌」校验(不符 403 `PARTICIPANT_FORBIDDEN`)。

### 踩坑(两个)
1. 过滤器**不做成 @Component**(否则 `@WebMvcTest` 会自动加载 Filter bean、拉出 DB 依赖)——由 SecurityConfig 手动构造。
2. **匿名认证过滤器**在我之前已给请求盖了「匿名身份」,原来的 `getAuthentication()==null` 判断失效、跳过了认证。改成「为空**或匿名**时才认参与者」。

### 验证 ✅(21 个测试全绿)
`TableJoinIntegrationTest` 含:带 token 读会话 200 / 无 token 401 / 跨会话 403 / **顾客 token 打店员接口 403(两道门隔离,对应设计验收「顾客凭证不能调店员接口」)**。
