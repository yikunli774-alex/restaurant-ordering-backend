## 先搞清一个最基础的分类:「库」还是「外部系统」?

你反复会看到两类东西,先分清,后面就不晕了:

| 类型 | 含义 | 怎么用 | 本项目的例子 |
|---|---|---|---|
| **库 / 框架(library)** | 别人写好的代码,**打包进你的程序里**一起跑 | 在 `pom.xml` 里写一行依赖,`import` 进来调用 | Spring Boot、Flyway、HikariCP、Spring Security、Nimbus(JWT) |
| **外部系统(external system)** | **单独运行的另一个程序**(常在另一个进程/另一台机器),你的程序通过**网络**连它 | 启动那个系统(我们用 Docker 启动),程序里配好「地址+端口」去连 | **MySQL**、**Redis**、(计划中的)**RocketMQ**、Nginx |

一句话:**MySQL / Redis / 消息队列都不是「import 进来的包」,而是「单独跑着、你连过去用」的服务器。** 你的 Java 程序里只放一个「连它的客户端库」。

> 举例:Redis 是一个独立的服务器程序(我们用 `docker` 起的 `redis:7-alpine` 容器)。Java 里只引入 `spring-boot-starter-data-redis`(客户端),然后配 `spring.data.redis.host=redis` 去连它。**Redis 本体和你的代码是两个进程。**

## 1. 数据库 / MySQL —— 数据要「持久、可靠」

**① 问题**:订单、账号、库存这些数据,如果只存在程序的内存里(变量里),程序一重启、一崩溃,数据全没。而且多台机器各存各的,对不上。

**② 后果**:重启丢单、丢账;没法多台机器共享同一份数据;没法保证「扣了库存」这件事真的落地。

**③ 我们的解法 & 为什么**:用**关系型数据库 MySQL** 做「唯一权威的、持久的数据源」。所有必须可靠保存的东西(店铺、桌台、会话、菜品、库存、订单、支付)都写进 MySQL。它把数据写进**磁盘**,断电重启也在;它有**事务**(见第 2 节)保证「要么全成要么全不成」;它有**唯一约束、外键、检查约束**这些「护栏」,从数据库层面兜底不让脏数据进来。

**④ 这东西到底是什么**:MySQL 是一个**独立运行的数据库服务器**(外部系统)。数据按「表」组织,一张表像 Excel(有列、有行)。你用 **SQL** 语言对它增删改查。我们的程序通过网络(默认 3306 端口)连它。

**⑤ 本项目里的具体代码**:

表结构不是手动在数据库里点的,而是写成 SQL 脚本由 Flyway 执行(见第 12 节)。例如「桌台会话」表,注意最后那个**生成列 + 唯一索引**——它用数据库自身保证「一张桌子同时只能有一个进行中的会话」(这是全项目最漂亮的一招,第 4 节细讲):

```sql
-- src/main/resources/db/migration/V3__create_tables_sessions_participants.sql
CREATE TABLE table_session (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    dining_table_id BIGINT UNSIGNED NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'OPEN',
    -- 会话进行中时,这一列 = 桌号;结束时 = NULL(数据库自动算)
    active_table_id BIGINT UNSIGNED GENERATED ALWAYS AS (
        CASE WHEN status IN ('OPEN','PENDING_PAYMENT') THEN dining_table_id ELSE NULL END
    ) STORED,
    PRIMARY KEY (id),
    CONSTRAINT uk_table_session_active UNIQUE (active_table_id)  -- 同一桌的活跃会话最多一个
);
```

Java 里我们用 `JdbcTemplate`(Spring 提供的、执行 SQL 的小工具)读写它:

```java
// src/main/java/.../table/TableSessionRepository.java
public Optional<String> findStatus(long sessionId) {
    return jdbc.query("SELECT status FROM table_session WHERE id = ?",
                    (rs, i) -> rs.getString("status"), sessionId)
            .stream().findFirst();
}
```

## 2. 事务 & 隔离级别 —— 一组操作「要么全成、要么全不成」

**① 问题**:下单要做好几件事:扣库存、建订单、记账。如果扣了库存,建订单时程序崩了,会怎样?

**② 后果**:库存扣了但订单没建 —— 库存凭空少了,数据不一致,对不上账。

**③ 我们的解法 & 为什么**:把这一串操作放进一个**事务(transaction)**。事务的规则是「**要么全部成功提交,要么全部撤销(回滚),绝不留半拉子**」。中途任何一步抛异常,前面做的全部自动撤销。

Spring 里加一个注解 `@Transactional` 就把一个方法包成事务:

```java
// src/main/java/.../order/OrderService.java
@Transactional(isolation = Isolation.READ_COMMITTED)
public RoundResult submitRound(long sessionId, String idempotencyKey) {
    // ... 扣库存、建订单、记账 —— 任何一步抛异常,以上全部回滚 ...
}
```

**关于 `isolation = READ_COMMITTED`(隔离级别)——这是个真实踩过的坑**:

**① 问题**:两个人同时给同一张桌子开会话。A 先建好并提交,B 紧接着想「查一下有没有已存在的会话」。

**② 后果**:MySQL 默认隔离级别是 `REPEATABLE READ`,它给每个事务一个「开始那一刻的快照」。B 在同一个事务里**看不到** A 刚提交的新会话(快照是旧的)→ B 以为没有 → 报错找不到。

**③ 解法 & 为什么**:把这类「找不到就新建、失败要重查」的操作,事务隔离级别设成 `READ_COMMITTED`——意思是「**每条语句都读最新已提交的数据**」。这样 B 重查时就能看到 A 的会话,顺利加入。

**④ 这东西到底是什么**:隔离级别 = 「一个事务能看到别的事务改了啥」的严格程度。从松到严有 4 档;`READ_COMMITTED`(读已提交)是很常用的一档:只读别人已提交的,不读没提交的。

**⑤ 代码**:就是上面那个 `@Transactional(isolation = Isolation.READ_COMMITTED)`。这一个参数,解决了「抢锁失败方重查看不到赢家」的问题。

## 3. Redis —— 给数据库减压 & 存「快、临时、要能秒删」的数据

**① 问题**:有些数据**读写极其频繁**(比如「购物车每加一个菜就改一次」「每个请求都要验一次登录状态」)。如果全丢给 MySQL:MySQL 要把每次改动落磁盘、还要保证事务,**慢**;高并发下大量这种小请求会把数据库**压垮**(连接被占满、磁盘 IO 打满、响应变慢甚至拖垮整个系统)。

**② 后果**:数据库成为瓶颈 → 所有功能都跟着卡 → 严重时数据库连接耗尽、请求排队、雪崩。

**③ 我们的解法 & 为什么**:把这类「高频、临时、不需要永久保存」的数据放进 **Redis**。Redis 把数据存在**内存**里(不是磁盘),读写是**微秒级**(比 MySQL 快几个数量级);它天生支持**过期时间**(到点自动删)和**原子操作**(见第 4 节的 Lua)。于是数据库只扛「必须持久」的核心数据,压力大减。

本项目用 Redis 存两样:
- **店员登录会话**:token 里只放个「会话号」,真正的权限存 Redis。**好处:登出/停用能「秒删」这条会话 → 旧 token 立刻失效**(纯 JWT 做不到,见第 7 节)。
- **购物车**:同桌多人共享一个购物车,频繁加减,存 Redis 最合适。

**④ 这东西到底是什么**:Redis 是一个**独立运行的内存数据库服务器**(外部系统,不是 import 的包)。可以把它想成一个「超快的、全局共享的大字典(key→value)」。我们用 Docker 把它跑起来:

```yaml
# compose.yaml —— Redis 是单独一个容器,和你的程序并列
services:
  redis:
    image: redis:7-alpine
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
```

**⑤ 本项目里的具体代码**:

Java 端只引入一个「客户端库」:
```xml
<!-- pom.xml -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>
```
配好去哪连(docker 里 Redis 这个服务就叫 `redis`):
```yaml
# application.yml
spring:
  data:
    redis:
      host: ${REDIS_HOST:localhost}
      port: ${REDIS_PORT:6379}
```
然后用 `StringRedisTemplate`(Spring 给的 Redis 客户端)读写。比如存一条登录会话:
```java
// src/main/java/.../staff/StaffSessionStore.java
public String create(long staffId, List<String> authorities) {
    String sessionId = UUID.randomUUID().toString().replace("-", "");
    String key = "staff:session:" + sessionId;
    redis.opsForHash().put(key, "staffId", String.valueOf(staffId));
    redis.opsForHash().put(key, "authorities", String.join(",", authorities));
    redis.expire(key, Duration.ofSeconds(ttlSeconds)); // 到点自动删
    return sessionId;
}
public void delete(String sessionId) {      // 登出 = 删这条 → token 立刻失效
    redis.delete("staff:session:" + sessionId);
}
```

## 4. 并发 & 竞态 —— 「很多人同时操作」为什么会算错

**① 问题**:很多请求**同时**操作同一份数据。经典场景:库存只剩 5 份,12 个人同时下单;或同桌两人同时点「结账」;或用户网络卡了、连点两下「加菜」。

**② 后果(专业词:竞态条件 race condition)**:
- **超卖**:12 个人各自「读到还有 5」→ 各自「扣 1」→ 卖出 12 份,库存变成 -7。
- **丢更新(lost update)**:两人同时改购物车,后写的把先写的覆盖了。
- **重复**:两次点击各建一张订单 / 各开一个会话。

**③ 我们的解法 & 为什么**:并发正确性是这个项目的**核心卖点**。我们**不用「读出来→改→写回去」这种会出错的方式**,而是用「一步到位、由底层保证原子」的手段。四招:

**招式 A:数据库唯一约束(让数据库拒绝重复)**
「一桌只能一个活跃会话」不靠应用层判断,靠第 1 节那个 `UNIQUE (active_table_id)`。并发下两个请求都想建 → 数据库只让一个成功,另一个撞唯一约束报错 → 我们**捕获这个错、改成「加入已存在的会话」**:
```java
// src/main/java/.../table/TableSessionRepository.java
public long findOrCreateActiveSession(long tableId) {
    Optional<Long> existing = findActiveSession(tableId);
    if (existing.isPresent()) return existing.get();
    try {
        jdbc.update("INSERT INTO table_session (dining_table_id, status) VALUES (?, 'OPEN')", tableId);
    } catch (DuplicateKeyException lostTheRace) {
        // 别人先建了 —— 正常,下面重查拿到他建的
    }
    return findActiveSession(tableId).orElseThrow();
}
```

**招式 B:条件更新(CAS,防超卖 / 防重复结账)**
扣库存不是「先查再减」,而是一条 SQL:`减库存,条件是「够减」`。数据库对这一行加锁、逐个串行执行,只有够库存的成功:
```java
// src/main/java/.../order/InventoryRepository.java
int rows = jdbc.update("""
    UPDATE inventory SET available = available - ?, reserved = reserved + ?
    WHERE menu_item_id = ? AND available >= ?""", qty, qty, menuItemId, qty);
// rows == 0 → 库存不够(或被别人抢走),返回失败;库存永远不会变负
```
这招也用在结账:`UPDATE ... SET status='PENDING_PAYMENT' WHERE status='OPEN'` —— 并发点结账,只有一个 `rows==1` 成功,其余 `rows==0`。这叫 **CAS(Compare-And-Swap,比较并交换)**。

**招式 C:Redis Lua 脚本(购物车原子增减)**
购物车「加 delta → 减到 0 就删这行 → 版本+1」必须**一次原子完成**,不能被别的请求插进来。Redis 支持把一段 Lua 脚本**当作一个不可分割的操作**执行:
```java
// src/main/java/.../cart/CartRepository.java  (MUTATE_LUA)
// 整段脚本在 Redis 里一次跑完,期间没有别的命令能插入
"""
local current = tonumber(redis.call('HGET', KEYS[1], ARGV[1]) or '0')
local newQty = current + tonumber(ARGV[2])
if newQty <= 0 then redis.call('HDEL', KEYS[1], ARGV[1]); newQty = 0
else redis.call('HSET', KEYS[1], ARGV[1], newQty) end
return {newQty, redis.call('HINCRBY', KEYS[2], 'version', 1)}
"""
```
**测试实证**:20 个线程同时对同一个菜 +1 → 最终数量恰好 20,一个都不丢。

**招式 D:幂等键(防重复提交)** —— 见第 5 节。

**④ 这些「招式」到底是什么**:它们都属于**并发控制**。核心思想是「**不要读-改-写(会有时间窗被人插队),而要用一条底层保证原子的操作**」:数据库的唯一约束 / 条件更新、Redis 的 Lua、幂等键。

**⑤ 简历价值**:这些都有**真并发测试**兜底(12 线程抢 5 库存→恰好 5 成功;10 线程并发结账→只出一张账单)。这就是你要的「能扛并发、不出错」的量化证据。

## 5. 幂等性 —— 「重复请求」为什么不能重复生效

**① 问题**:网络会重发。用户点「加菜」,网卡了没收到响应,他又点一下;或客户端自动重试。服务器收到了**两次同样的请求**。

**② 后果**:下了两张单、扣了两次库存、(将来)扣两次钱。

**③ 我们的解法 & 为什么**:让「同一个操作做一次和做多次,结果一样」——这就叫**幂等(idempotent)**。做法:每个下单请求带一个唯一的 **`Idempotency-Key`**(幂等键,客户端生成)。服务器把「这个 key → 生成的订单」记在一张表里。**同一个 key 再来,直接返回上次那张单,不再执行一遍。**

**④ 这东西到底是什么**:幂等键就像电梯按钮——按 5 次和按 1 次效果一样。它是「防重复」的通用手段。

**⑤ 本项目里的具体代码**:
```sql
-- V5__create_order_rounds.sql
CREATE TABLE api_idempotency (
    scope VARCHAR(40) NOT NULL, idempotency_key VARCHAR(80) NOT NULL,
    result_id BIGINT UNSIGNED NOT NULL,
    PRIMARY KEY (scope, idempotency_key)   -- 同一个 key 只能有一条
);
```
```java
// src/main/java/.../order/OrderService.java
public RoundResult submitRound(long sessionId, String idempotencyKey) {
    var replay = orderRepository.findIdempotentResult(SCOPE, idempotencyKey);
    if (replay.isPresent()) return loadResult(replay.get()); // 重放 → 返回同一张单
    // ... 真正下单 ... 最后 orderRepository.insertIdempotency(SCOPE, idempotencyKey, roundId);
}
```
**测试实证**:同一个 key 提交两次 → 只有一张单、库存只扣一次。

## 6. 消息队列(RocketMQ)—— 「异步解耦」(本项目暂缓,但要懂为什么需要)

> 说明:这块目前**还没接**,但设计里预留了。这里讲清「为什么最终会用它」。

**① 问题**:顾客点「加菜」下单后,理想是**后厨屏幕立刻弹出新单**。如果用「同步」方式做——下单请求里顺便去通知后厨、发短信、更新统计……

**② 后果**:
- **慢**:下单要等所有这些附带操作都干完才返回,顾客等得久。
- **脆**:其中任一步(比如通知后厨的服务)挂了,整个下单就失败。
- **推不动**:HTTP 是「客户端问、服务器答」,服务器没法主动「推」消息给后厨屏幕。

**③ 解法 & 为什么**:引入**消息队列**。下单时只做核心的事(扣库存、建单),然后往队列里**扔一条消息「有新单了」**就立刻返回。后厨服务作为「消费者」在另一头**订阅**这条消息,收到就更新屏幕。这样:下单快(不等后厨);解耦(后厨服务挂了不影响下单,消息在队列里等着);可异步、可重试。

配套的 **Outbox 模式**:为了保证「订单入库」和「消息发出」不会一个成一个败,先把消息也写进数据库(和订单同一个事务),再由一个后台任务捞出来发到队列——确保消息不丢。

**④ 这东西到底是什么**:消息队列(RocketMQ / Kafka / RabbitMQ 等)是一个**独立运行的「消息中转站」服务器**(外部系统)。一边「生产者」往里放消息,另一边「消费者」取消息。像餐厅的「出单机」:前台把单子打出来,后厨自己去取。

**⑤ 代码**:目前后厨看新单靠「轮询」(前端每隔几秒查一次 `GET /rounds`)。接入 RocketMQ 后会变成「推送」。这是后续任务。

## 7. 鉴权:JWT vs 服务端会话 —— 「你是谁」怎么证明、怎么作废

**① 问题**:店员登录后,后续每个请求怎么证明「我已经登录了、我是谁」?总不能每次都传密码。

**② 后果**:要么每次查数据库验密码(慢),要么身份没法验证(不安全)。

**③ 我们的解法 & 为什么**:登录成功发一张**JWT(电子通行证)**——一段签了名的字符串,里面写着「你是谁 + 过期时间」。之后每次请求带上它,服务器**验签名**就知道是谁,**不用查数据库**(快)。

但 JWT 有个硬伤:**发出去就没法提前作废**(服务器不存它,只验签名),用户登出/被停用后,旧 JWT 还能用到过期。**所以我们加了 Redis 服务端会话**:JWT 里只放「会话号」,权限存 Redis;每个请求验完签名再去 Redis 查「这个会话还在不在」——**登出 = 删 Redis 会话 → 旧 JWT 立刻失效**。两者结合:既快(验签名),又能秒作废(查 Redis)。

**④ 这东西到底是什么**:
- **JWT**:一段 `header.payload.signature` 的字符串,签名用密钥保证没被篡改。是「无状态」的(服务器不用存)。
- **服务端会话**:把登录状态存在服务器端(这里是 Redis),能主动删除。

**⑤ 本项目里的具体代码**:签发(登录时)——注意 token 里**只放 sid(会话号),不放权限**:
```java
// src/main/java/.../staff/StaffAuthService.java
String sessionId = sessionStore.create(staff.id(), authorities); // 权限进 Redis
JwtClaimsSet claims = JwtClaimsSet.builder()
        .subject(String.valueOf(staff.id())).claim("sid", sessionId) // token 只放 sid
        .expiresAt(now.plusSeconds(accessTtlSeconds)).build();
```
校验(每个请求)——验完签名再查 Redis,查不到就当作已吊销(**fail closed,失败就拒绝**):
```java
// src/main/java/.../staff/StaffJwtAuthenticationConverter.java
var session = sessionStore.find(jwt.getClaimAsString("sid"))
        .orElseThrow(() -> new InvalidBearerTokenException("Session revoked or expired"));
// 权限从 Redis 会话取(不从 token 取)→ 改权限能立刻生效
```
**测试实证**:登录拿 token → 能访问 → 登出 → **同一个还没过期的 token 再访问,直接 401**。

## 8. RBAC & HMAC 签名 —— 「你能干什么」& 「防伪」

**RBAC(基于角色的访问控制)**

**① 问题**:后厨能看单、但不能改菜价;店长啥都能干。怎么管「谁能干什么」?

**② 后果**:不管的话,要么谁都能干(不安全),要么给每个人单独配一堆权限(乱)。

**③ 解法 & 为什么**:**角色←→权限、人←→角色** 两层。定义角色(KITCHEN、MANAGER),角色绑一组权限(`menu:manage` 等),人分配角色。改权限只改角色。

**⑤ 代码**:接口上一句注解就按权限拦截(后厨没有 `menu:manage` → 自动 403):
```java
// src/main/java/.../menu/MenuManagementController.java
@PostMapping("/menu-items")
@PreAuthorize("hasAuthority('menu:manage')")   // 只有具备该权限的人能进
public CreatedResponse create(...) { ... }
```

**HMAC 签名(防伪)**

**① 问题**:桌台二维码里如果只写「T01」,有人把它改成「T99」蹭别桌怎么办?

**② 后果**:能伪造桌号、蹭单、扰乱。

**③ 解法 & 为什么**:二维码里放「桌号 + **签名**」。签名 = 用服务器密钥对桌号算一段 **HMAC**。改了桌号,签名对不上,服务器验签直接拒。密钥只有服务器有,别人伪造不出签名。

**④ 这东西到底是什么**:HMAC = 用一个「密钥」+ 一段数据,算出一段没法逆推、改一个字就全变的「指纹」。验的时候用同样的密钥重算一遍比对。

**⑤ 代码**:
```java
// src/main/java/.../table/TableCodeSigner.java
public String sign(String code) { return code + "." + hmac(code); } // 二维码内容
public String verify(String token) {                                 // 扫码后验
    // 拆出 code 和签名,用同一密钥重算 hmac(code) 比对,不一致就抛错
}
```

## 9. Docker & 容器 —— 「在我机器上能跑」怎么变成「哪都能跑」

**① 问题**:一个后端要跑起来,需要:装对版本的 Java、装 MySQL、装 Redis、配一堆参数。换台机器(同事的、服务器的)又要重来一遍,还经常「我这能跑你那不行」。

**② 后果**:环境配置地狱、部署困难、「在我机器上是好的」扯皮。

**③ 解法 & 为什么**:用 **Docker** 把「程序 + 它需要的环境」打包成一个**镜像**,任何装了 Docker 的机器一条命令就能一模一样地跑起来。MySQL、Redis 也各自用现成镜像跑,不用手动装。

**④ 这东西到底是什么**:
- **镜像(image)**:打包好的、只读的「程序+环境」模板,像一张系统安装光盘。
- **容器(container)**:用镜像跑起来的运行实例,像用光盘装出来、正在运行的一台「虚拟小电脑」。
- **docker compose**:用一个 `compose.yaml` 一键起一堆容器并把它们连起来。

**⑤ 本项目里的具体代码**:`Dockerfile`(怎么打包我们的程序)、`compose.yaml`(一键起 MySQL + Redis + 两个后端 + Nginx):
```yaml
# compose.yaml(节选)
services:
  mysql: { image: mysql:8.4, ... }
  redis: { image: redis:7-alpine, ... }
  app-1: { image: restaurant-ordering-backend:local, ... }
  app-2: { image: restaurant-ordering-backend:local, ... }
  nginx: { image: nginx:1.28-alpine, ports: ["8080:8080"], ... }
```

## 10. 双实例 + Nginx + 无状态 —— 「一台不够 / 会挂」怎么办

**① 问题**:只跑一个后端进程:它挂了服务就没了(单点故障);用户一多它扛不住(单点瓶颈)。

**② 后果**:不可用、扛不住高峰。

**③ 解法 & 为什么**:**同一个程序跑两份(app-1、app-2)**,前面架一个 **Nginx** 把请求轮流分给它们(负载均衡)。一个挂了另一个还在,量大了可以加更多份。

**但这带来一个关键要求:程序必须「无状态」。** 意思是:不能把「登录状态、购物车」这种数据存在**某个进程自己的内存里**——因为 Nginx 可能这次把你分给 app-1、下次分给 app-2,如果状态存在 app-1 内存里,app-2 就不认识你了。**所以这些共享状态必须放进 Redis / MySQL 这种「大家都能连的外部系统」。** 这也是第 3 节「为什么用 Redis 存会话/购物车」的深层原因之一。

**④ 这东西到底是什么**:
- **负载均衡(load balancing)**:一个「分流员」把流量分摊到多台后端。
- **无状态(stateless)**:每个后端实例自己不保存「跨请求的用户状态」,状态都在外部(Redis/MySQL)。

**⑤ 代码**:
```nginx
# deploy/nginx/nginx.conf
upstream ordering_backend {
    least_conn;            # 谁当前更闲发给谁
    server app-1:8080;
    server app-2:8080;
}
```
**实证**:第 7 节的真机演示,是经 Nginx 轮流打到两个实例的,因为会话在共享 Redis 里,所以「在 app-1 登录、请求被 app-2 处理」也认得你。

## 11. 连接池(HikariCP)—— 「连数据库很贵」

**① 问题**:每次要查数据库都新建一个 TCP 连接、用完关掉。建连接要握手、认证,**很慢很贵**。高并发下每秒建关成千上万个连接,数据库和程序都受不了。

**② 后果**:响应慢、资源浪费、数据库连接被打满。

**③ 解法 & 为什么**:用**连接池**:程序启动时先建好一小批连接**放在池子里**,谁要用就借一个、用完还回去(不真的关闭),重复利用。省掉反复建连接的开销。

**④ 这东西到底是什么**:连接池是一个「管理复用数据库连接的库」(**import 进来的**,不是外部系统)。Spring Boot 默认用 **HikariCP**。

**⑤ 代码**:我们几乎不用写代码——加了 JDBC 依赖后 Spring Boot 自动装配 HikariCP,只在配置里调下大小:
```yaml
# application.yml
spring:
  datasource:
    hikari:
      maximum-pool-size: ${DB_POOL_SIZE:10}
```

## 12. Flyway —— 「数据库表结构怎么跨机器管理」

**① 问题**:表结构会不断变(加表、加列)。手动在每台机器(本地、测试、生产)的数据库里改,极易漏改、改错、对不上。

**② 后果**:各环境表结构不一致,程序在一台好使、另一台报错。

**③ 解法 & 为什么**:用 **Flyway** 做「数据库版本管理」。每次表结构变更写成一个**编号的 SQL 脚本**(`V1__`, `V2__`…),Flyway 按顺序执行、并在一张 `flyway_schema_history` 表里记录「做过哪些」。任何机器从空库开始,一键就能重建出完全一样的结构,且只执行没执行过的。

**④ 这东西到底是什么**:Flyway 是个**库**(import 进来),程序启动时自动跑迁移。

**⑤ 代码**:就是 `src/main/resources/db/migration/` 下那一串 `V1__...sql` ~ `V6__...sql`。我们从不手动改数据库,全靠这些脚本。

## 13. Testcontainers —— 「测试要对着真环境,不能用假的」

**① 问题**:写自动化测试时,总不能连生产数据库。有人图省事用「内存假数据库」(H2)。

**② 后果**:H2 装不像 MySQL——我们最依赖的「生成列 + 唯一索引」「MySQL 的行锁行为」「NULL 在唯一索引里的处理」,H2 都可能表现不同。**测试过了,上线却挂**——等于白测。

**③ 解法 & 为什么**:测试时用 **Testcontainers** 临时**用 Docker 起一个真的 MySQL / 真的 Redis** 容器,测完自动销毁。测的就是真环境,没有「假的骗过测试」。

**④ 这东西到底是什么**:Testcontainers 是个**测试库**(import 进来,只在测试时用),它在测试期间帮你启停 Docker 容器。

**⑤ 代码**:
```java
// src/test/java/.../TestcontainersConfiguration.java
@Bean @ServiceConnection
MySQLContainer<?> mysqlContainer() { return new MySQLContainer<>(DockerImageName.parse("mysql:8.4")); }
@Bean @ServiceConnection(name = "redis")
GenericContainer<?> redisContainer() { return new GenericContainer<>("redis:7-alpine").withExposedPorts(6379); }
```
我们全部 **47 个测试**都跑在真 MySQL + 真 Redis 上。

## 14. 统一错误 + 追踪 ID —— 「线上出问题怎么查」

**① 问题**:每个接口出错各返回各的格式;线上报错,几万条日志里根本找不到「就是这一次请求」出的问题。

**② 后果**:前端难处理错误;排查问题像大海捞针。

**③ 解法 & 为什么**:
- **统一错误格式**(Problem Details 标准):所有错误都返回同一种 JSON,带稳定错误码(如 `INSUFFICIENT_STOCK`)。前端靠错误码判断,可靠。

**⑤ 代码**:
```java
// src/main/java/.../common/api/GlobalExceptionHandler.java —— 全局统一处理
@ExceptionHandler(ApiException.class)
ProblemDetail handleApi(ApiException e) { return baseProblem(e.status(), e.code(), e.getMessage()); }
```
```java
// src/main/java/.../common/api/TraceIdFilter.java —— 每个请求盖唯一编号
String traceId = UUID.randomUUID().toString().replace("-", "");
response.setHeader("X-Trace-Id", traceId);
```

## 15. 状态机 —— 「一个业务对象允许怎么变」

**① 问题**:会话、订单这类对象有多种状态(进行中/待支付/已关闭…)。如果不明确规定「从哪能走到哪」,代码里到处散落 if-else,总会漏——比如关了桌还能加菜、付过款还能再付。并发下更糟:两个请求同时检查「当前是 OPEN」都通过,然后都执行。

**② 后果**:非法状态转移 → 重复支付、幽灵订单、账目错乱。

**③ 我们的解法 & 为什么**:先在设计里画清**状态机**(状态 + 合法转移边),再用两道闸实现:
- **条件更新(CAS)**:把「必须处于 X 状态」写进 UPDATE 的 WHERE(如 `WHERE status='OPEN'`),数据库原子把关,并发下也只有一个请求能完成转移;
- **CHECK 约束**:`CHECK (status IN (...))`,非法状态值根本存不进去。

**④ 这东西到底是什么**:状态机 = 「对象生命周期的地图」:有限的状态集合 + 允许的转移边。**注意:它和"页面跳转"无关**——页面导航是前端路由;状态机管的是业务数据的合法演化。

**⑤ 本项目里的具体代码**:两个状态机。
- 会话:`OPEN →(结账)→ PENDING_PAYMENT →(支付)→ CLOSED`,转移见 `CheckoutRepository.startCheckout / closeAsPaid`(都是 `UPDATE ... WHERE status=...` 的 CAS);「结账中不能加菜」= 下单前校验 `status='OPEN'`(`OrderService.submitRound`)。
- 订单轮次:`CONFIRMED → PREPARING → READY → COMPLETED`(+ `CANCELLED`),状态列和 CHECK 约束在 `V5__create_order_rounds.sql`;转移接口即「后厨看板」功能。

## 一句话总览

这个项目的主线是:**用 MySQL 存必须可靠的数据 + Redis 扛高频临时数据 + 一堆「并发正确」的手段(唯一约束、条件更新 CAS、Redis 原子 Lua、幂等键)保证「很多人同时用也不算错」,再用 Docker 双实例 + Nginx 把它做成「可扩展、无状态」的生产级部署,全程有真环境测试兜底。** 消息队列(实时推送)和并发压测数字是收尾的两块。
